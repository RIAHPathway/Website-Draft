## I. Purpose
Examine publicly accessible source repositories and documentation for independently verifiable similarities with RIAH Pathway's *documented* website and ecosystem design. Search GitHub first, then public GitLab, Codeberg, SourceHut, Bitbucket, educational open-source projects, and public organization websites where genuinely accessible. Record relevant public repository owners, verified public contributors, feature-level evidence, repository URLs, dates, scope, and meaningful daily changes.

The bot is an **evidence collection and comparison system**, not a plagiarism detector, legal decision-maker, assertion of exclusivity, or proof that another project derived from RIAH Pathway. Similar topics, filenames, navigational categories, business models, or features do not by themselves demonstrate copying, shared implementation, or legal wrongdoing.

## V. Evidence-Based Classification
| Label | Required documented finding |
|---|---|
| 🟢 Tier I — Component | One independently documented feature comparable with one specific RIAH baseline component. |
| 🟡 Tier II — Connected | At least two relevant corresponding functions demonstrably linked in one identifiable program or repository, with their connection cited. |
| 🔴 Tier III — Complete | Independently documented correspondence across the whole RIAH A–Z architecture: six pillars, nine school/pathway categories, eight entity functions where genuinely comparable, exact experiential progression, credential and bar review, contributions and economic benefits, tuition/products, entrepreneurship, technology, and career. All required connections need affirmative evidence. |
| 🔵 Insufficient | Available record cannot establish the proposed match level; document precisely what was missing. |
| ⚫ Not in scope | Source not meaningfully relevant after review. |

Tier labels refer to **comparison breadth**, not risk, culpability, originality, priority, infringement, or proof of derivation. Explicitly separate *topic match*, *structural match*, *textual match*, *code match*, *fork lineage*, and *independent historical chronology*. Only state that a repository was derived from RIAH when public fork lineage or equivalent direct provenance is verified.

## VII. Daily Execution Contract
1. Read RIAH main branch, controlling documents, prior watch log, prior evidence register, and prior recorded baseline SHA.
2. Capture date and time at *actual available precision*, time zone, source URLs and RIAH git-tree SHA. Compare with the prior snapshot using available tools; label first run as baseline.
3. Validate sitemap 1–20, page folders, actual Markdown files, routing references and broken local links; report only verified defects and distinguish empty scaffold folders from absent folders.
4. Search GitHub repositories and code; use alternate public hosting and web-indexed documentation where accessible; retain query/source coverage and exclude noisy results.
5. For each potentially relevant repo, read actual README or other source file and public provenance/commit records; identify verified contributor handles. Check whether the findings are old, newly published or merely newly discovered.
6. Apply the tier evidence tests without inferring copying from overlap. Include side-by-side RIAH baseline / external feature / connection / missing features / link / feature evidence date.
7. Compare candidates to existing register; permanently preserve first discovery; update last verification only following a new examination. Distinguish first bot discovery from original repository creation and original feature implementation.
8. Append one distinct dated section to RUN-LOG.md; preserve all old entries. Include scan summary, per-topic status, named candidates, contributor evidence, internal integrity checks, tier counts, change since last run, limitations, next checks.
9. Update EVIDENCE-REGISTER.md when new findings or verifications occurred. Commit changes to RIAHPathway/Website-Draft on main with **exact message: RIAH Pathway.** Do not edit any RIAH ecosystem source, sitemap, legacy bot record or license unless separately requested.
10. On GitHub write failure, **do not claim a push succeeded**. Present the unsaved findings and exact error. On search failure, do not infer zero matches.
11. If the daily automation triggers again on the same local date, check for an existing run entry and append a time-marked amendment instead of falsely creating a second daily baseline.
